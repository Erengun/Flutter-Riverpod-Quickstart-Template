# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repo layout

The repo is a Dart pub workspace. The root `pubspec.yaml` is workspace-only (`publish_to: none`, `workspace:` list, Melos config under `melos:`) and holds no code. One `pubspec.lock` and one `.dart_tool/` live at the root.
- `app/`: the whole app (pubspec, `lib/`, `test/`, `assets/`, platform folders). App paths below are relative to `app/`.
- `packages/core/` (package `core`): infrastructure every app gets. It depends on nothing else in the repo. It holds `bootstrap`, per-flavor config, the network layer (shared Dio, `ApiException`, `apiCall`), the session layer (encrypted Hive boxes, `Session`, the auth interceptor, the router redirect), permissions (`Permissions`, loading and reloading, the route guard, `PermissionGate`, the menu filter, the no-permission and under-construction pages), the Module contract, the `ErrorReporter` / `Analytics` / `RemoteFlags` interfaces, logging and error-report dispatch, and the router transition extensions and navigation observer; import it via `package:core/core.dart`.
- `packages/firebase_module/`: optional Module (android, ios, web) contributing Firebase `Analytics` and Remote Config `RemoteFlags`; depends only on Core. Its options files in `lib/src/options/` are placeholders that throw `FirebaseNotConfiguredException` until `melos run firebase:configure:<flavor>` overwrites them; they are lint-excluded. Setup, the iOS ad-id env var and the removal checklist are in the README's "Firebase Module" section.
- `packages/sentry_module/` (package `sentry_module`): the `SentryModule` (`sentry_flutter` ^9, all six platforms). Dev never starts Sentry and contributes the no-op reporter; staging and prod start it with `environment` = flavor name, errors and crash-free statistics only (no tracing, replay, screenshots, PII, HTTP capture or Sentry logs). One DSN constant, `sentryDsn` in `lib/src/sentry_options.dart`, ships empty; while it is empty Sentry never starts. `SentryFlutter.init` runs without `appRunner` (Core calls `runApp`), and its error integrations chain to Core's uncaught-error handlers; on web `configureSentryOptions` adds the `OnErrorIntegration` sentry_flutter leaves out there, fed by Core's `runGuarded` zone.
- `widgetbook/` (package `widgetbook_catalog`): the web-only Widgetbook catalog (only a `web/` platform folder). It depends on the app, Core and each Module; the app never depends on it, and removing a Module removes its line from `widgetbook/pubspec.yaml` and its use cases. Use cases are `@UseCase` functions in files that mirror the widget's path (`lib/core/permission_gate.use_cases.dart`, `lib/app/features/home/presentation/home_screen.use_cases.dart`); `melos run gen` regenerates the committed `lib/main.directories.g.dart`. Addons are in `lib/catalog/catalog_addons.dart`: device frame, locale, text scale, accessibility, theme. The theme addon comes last because it wraps each use case in `CatalogApp`, a material_ui `MaterialApp` (Widgetbook's shell is `flutter/material`, whose `Theme` and `ScaffoldMessenger` the app's widgets can't see) that also maps the app's unprefixed asset keys to `packages/flutter_riverpod_template/`. Screens that use Riverpod get their own root `ProviderScope` with the tests' fakes (`lib/app/demo_scope.dart`); there is none above the catalog. Run it with `melos run widgetbook`. The root pubspec overrides `analyzer` only because `widgetbook_generator` caps it below 14; the generator's telemetry is off in `widgetbook/build.yaml`. Run, publish and removal steps are in the README's "Widgetbook" section.
- Every package has its own `test/` and an `analysis_options.yaml` that includes the root one (plus its own `exclude:` globs, since excludes resolve relative to the file that declares them).
- New packages go in `packages/` and must be added to the root `workspace:` list; each member's pubspec has `resolution: workspace`. The app depends on `core` by `path: ../packages/core`.

## Commands

Run from the repo root unless noted. Melos 7 is a root dev dependency, so call it as `dart run melos ...` (or a global `melos`).
- Install deps: `flutter pub get` (resolves every workspace member and runs gen-l10n in every package with an `l10n.yaml`, regenerating `lib/l10n/*_localizations*.dart`; commit them). Inside one package, `flutter gen-l10n` does the same.
- Codegen in every package that uses build_runner (Riverpod, Freezed, json_serializable, retrofit clients, Hive CE adapters; Core too, for `BaseResponse`): `dart run melos run gen`. While iterating in the app: `dart run build_runner watch --delete-conflicting-outputs` from `app/`. Rerun after changing any `@riverpod`, `@freezed`, `@JsonSerializable`, or `@GenerateAdapters` code. Generated `*.g.dart` / `*.freezed.dart` files are committed, so commit regenerated output alongside source changes.
- Tests in every package: `dart run melos run test`. Inside one package (`cd app` or `cd packages/core`): `flutter test`; single file: `flutter test test/features/login_controller_test.dart`; single test: add `--plain-name "successful login updates state correctly"`.
- Analyze every package (matches CI): `dart run melos run analyze` (runs `flutter analyze --no-pub --fatal-infos --fatal-warnings` and `dart analyze --fatal-infos --fatal-warnings` per package).
- Run (flavors), from `app/`: `flutter run --flavor dev -t lib/main_dev.dart` (also `staging` / `lib/main_staging.dart`, `prod` / `lib/main_prod.dart`). VS Code launch configs for all three flavors are committed in `.vscode/launch.json`.

Flutter must be `>=3.47.4` (root pubspec `environment`); CI always uses the latest stable.

CI (`.github/workflows/ci.yaml`, every PR to `main` and every push to `main`; no job needs secrets). All four jobs are meant to be required checks, but the workflow does not enforce that: a repo admin turns it on in branch protection for `main` ("Use this template" does not copy that setting). Shared setup is the composite action `.github/actions/setup` (Flutter stable with caching, `flutter pub get`, Melos at the version in the root `pubspec.lock`); each job checks out first, then uses it.
- `check`: `melos run gen`, then fails if any `*.g.dart` / `*.freezed.dart` file or generated `lib/l10n/*_localizations*.dart` changed or is untracked (so always commit regenerated files), then `melos run analyze` (any lint info fails), then `melos run test` (`--coverage`; the coverage artifact never blocks). No format check.
- `build-android`, `build-ios` (`--no-codesign`), `build-web`: unsigned prod release builds from `app/` with `-t lib/main_prod.dart` (plus `--flavor prod` on Android/iOS). `build-ios` fails if `app/ios/Podfile` appears: every iOS plugin must support Swift Package Manager.
- Runner labels come from repo variables `LINUX_RUNNER` / `MACOS_RUNNER` (defaults `ubuntu-latest` / `macos-latest`). A new push to a PR cancels its older runs.
- `.github/workflows/widgetbook.yaml` (push to `main` and manual dispatch) builds `widgetbook/` for the web and deploys it to GitHub Pages, only when the repo variable `WIDGETBOOK_PUBLISH` is `'true'` (and Pages' source is "GitHub Actions"). PRs have no Widgetbook job: `check` already generates, analyzes and tests it, and its `*.g.dart` check covers `main.directories.g.dart`.
- Dependabot (`.github/dependabot.yml`) updates pub (root, `app/`, `packages/*`, `widgetbook/`), GitHub Actions and Bundler weekly. New packages under `packages/` are picked up by the glob.

## Lint rules

`lint_rules.yaml` enables almost every Dart lint; the root `analysis_options.yaml` turns off the conflicting ones and adds the analyzer plugins (below) plus strict-casts/inference/raw-types. Each package includes it. In practice:
- Explicit types everywhere (`always_specify_types`): `final String x = ...`, typed collection literals (`<Locale>[...]`), typed closure params.
- Relative imports inside a package's `lib/` (`prefer_relative_imports`); other packages via `package:core/...`; app tests import via `package:flutter_riverpod_template/...`.
- Single quotes.
- No imports between Features (`no_cross_feature_imports`): a file in `lib/features/<a>/` must not import or export anything from `lib/features/<b>/`. Move shared code to Core or `lib/shared/`, or navigate through the router. Files outside a Feature folder (`lib/app/`, `test/`) may import any Feature.
- Only `lib/app/theme.dart` imports `lib/app/tokens.dart` (`tokens_only_in_theme`, also for tests and other packages). Everything else reads tokens through `Theme.of(context)` or `KonteynerTokens.of(context)`.

**Analyzer plugins.** The root `analysis_options.yaml` loads three plugins: `riverpod_lint`, `packages/konteyner_lints` (the template's architecture rules, currently `no_cross_feature_imports` and `tokens_only_in_theme`) and `packages/app_lints` (empty; an app adds its own rules there, registered in its `lib/main.dart` the same way). The two local plugins are referenced by `path:`, are not workspace members (they have their own `pubspec.lock`) and report in every package that includes the root options. Notes:
- Only `dart analyze` runs plugins; `flutter analyze` does not, so a clean `flutter analyze` alone proves nothing for plugin rules. The Melos `analyze` script runs both.
- Rule tests use `analyzer_testing` (`AnalysisRuleTest`, see `packages/konteyner_lints/test/`). Run them with `dart run melos run test:lints` (also part of `melos run test`); `melos run analyze:lints` analyzes both plugin packages (also part of `melos run analyze`).
- `analysis_server_plugin` is 0.x and pinned to an exact version, with `analyzer` pinned to the version it requires. Bump both together in both plugin packages. After changing a plugin, restart the analysis server (or rerun `dart analyze`) to pick it up.

## Architecture

**Entry / flavors.** Each of `app/lib/main_dev.dart` / `main_staging.dart` / `main_prod.dart` runs the app-owned `setUpApp()` (`lib/app/setup.dart`: Hive, orientation) and then calls Core's `bootstrap(<flavor>Config, app:, theme:, splash:, modules:, overrides:)` with its config from `lib/app/config.dart`, the theme from `lib/app/theme.dart` and the Modules from `lib/app/modules.dart`. `overrides:` (optional) takes the app's own `ProviderScope` overrides from `lib/app/overrides.dart` (`buildAppOverrides()`, which overrides `sessionHooksProvider` with the auth Feature's `authSessionHooks`); it must not repeat a provider `bootstrap` already overrides (config, theme, splash, Module interfaces). Bare `lib/main.dart` is dev, and the app pubspec sets `flutter: default-flavor: dev`, so a plain `flutter run` / `flutter build` never points at prod. On Android and iOS `bootstrap` throws `FlavorMismatchError` before `runApp` when the native `--flavor` differs from the entrypoint, in every build mode; elsewhere the entrypoint alone decides. No `--dart-define`: edit the configs instead. Native flavor names/IDs live in `android/gradle.properties` (`app.*` keys, read by `android/app/build.gradle.kts`) and `ios/Flutter/{Debug,Profile,Release}-<flavor>.xcconfig`; keep them in sync with Core's `Flavor { dev, staging, prod }`.

**Config.** Core's `AppConfig` holds only per-flavor values: `flavor`, `apiBaseUrl`, the demo `apiKey` and `storeLinks` (force-update store ids/links; empty means no check). Read it with `ref.watch(appConfigProvider)`; the provider throws unless `bootstrap` overrides it, so tests use `appConfigProvider.overrideWithValue(...)`. A Module's or Feature's own per-flavor values (a DSN, a second base URL) stay in that Module or Feature and are picked by `config.flavor`. Nothing compiled into the app is secret.

**Modules.** A Module implements Core's `KonteynerModule` (`name`, `platforms`, `Future<ModuleContributions> init(AppConfig config)`) and is listed in `lib/app/modules.dart`. `bootstrap` starts them in order through `startModules`: a Module is skipped on platforms outside `platforms`; a throwing `init` is logged, keeps the defaults and is reported once every Module has started; two Modules contributing the same interface stop startup with `ModuleConflictError`. Contributions become `ProviderScope` overrides of `errorReporterProvider`, `analyticsProvider` and `remoteFlagsProvider`, whose defaults are the no-op `NoopErrorReporter` / `NoopAnalytics` / `NoopRemoteFlags`. Modules never write overrides themselves.

**Force update.** `KonteynerUpdateGate` sits in `MaterialApp.router`'s `builder` (in `MyApp`) with the router's navigator key. It reads `app_min_version_<platform>` / `app_recommended_version_<platform>` (`x.y.z` version names) through `appVersionSourceProvider`, which defaults to `RemoteFlags`; an app whose backend serves the versions overrides that provider. Below the minimum: a dialog with only Update that can't be dismissed. Below the recommended: Update / Ignore / Later. The dialog is Core's public `KonteynerUpdateDialog` (material_ui, Core's strings), which the Widgetbook catalog shows on its own since the gate never checks on web. An empty `storeLinks` entry means no check on that platform; web is never checked. Startup never waits: cached values are checked at once, `RemoteFlags.refresh()` runs in the background, and the check repeats on resume and on `RemoteFlags.onChanged`. Any failure lets the user in. Raise the Android minimum only after the new build is fully rolled out on Play.

**Logging and error reporting.** Three channels: a log (developer line), a breadcrumb (short note attached to the next report) and an error report (sent through `ErrorReporter.report`).
- Log through named loggers from the `logging` package, one per Feature or area: `static final Logger _log = Logger('auth');`. Nothing wraps `logging`; `bootstrap` attaches the only root-logger listener (`configureLogging` in `packages/core/lib/src/logging/log_setup.dart`). Outside Core's console printer, never use `print`, `debugPrint` or `dart:developer` `log`.
- Levels per flavor (`LogPolicy.forFlavor`): dev keeps `ALL` and prints, staging keeps `INFO` and prints, prod keeps `INFO` with no console. The console printer writes through `debugPrint`, which `bootstrap` silences only in prod release builds.
- Kept records at `INFO` and above become breadcrumbs (category = logger name). A record carrying an error never does. Feature and app code logs; it never calls `addBreadcrumb` directly (Core infrastructure that needs structured `data` may).
- Never log headers, bodies, query values, tokens, passwords or personal data: every log line may reach the error tracker.
- To record an exception, call `ref.read(errorReporterProvider).report(error, stackTrace)`, not `log.warning(msg, error)`. A log record with an error attached is Core's own echo of a report or an uncaught error.
- `errorReporterProvider` is Core's `ReportDispatcher`: every `report` is first logged at `SEVERE`, then sent to the Module's reporter. Until every Module has started, reports are buffered and breadcrumbs dropped.
- `bootstrap` installs log-only `FlutterError.onError` / `PlatformDispatcher.onError` before Modules start (an error-tracker Module chains to them; Core never reports uncaught errors), and each `main_<flavor>.dart` wraps its body in `runGuarded`: on web, whose engine never calls `PlatformDispatcher.onError`, it runs the body (binding init included) in a zone that forwards uncaught async errors to that handler; elsewhere it adds no zone. `bootstrap` also adds `ProviderFailureObserver` to the `ProviderScope`: a failed provider (thrown in `build` or an `AsyncError` state) is reported once per provider per launch, repeats become breadcrumbs, and `ApiException` (Core's marker for errors the network layer already handled) is skipped. Errors handled without failing a provider need an explicit `report`.
- Tests: `configureLogging(..., printer: records.add)` captures records; call `resetLogging()` in `tearDown`. A test that runs `bootstrap` must restore `FlutterError.onError` and `PlatformDispatcher.instance.onError` inside the test body (see `packages/core/test/bootstrap/bootstrap_test.dart`).

**State management.** Riverpod 3 with code generation (`@riverpod` / `@Riverpod(keepAlive: true)` + `part '*.g.dart'`). Generated provider names are `<name>Provider` (e.g. `authenticationRepository` → `authenticationRepositoryProvider`). Immutable models and UI state use Freezed.

**Features** (`lib/features/<feature>/{data,domain,presentation}`):
- `domain/`: Freezed request/response models and use cases.
- `data/`: repositories. An abstract interface plus implementation exposed through a provider (e.g. `AuthenticationRepository` / `HttpAuthRepository` via `authenticationRepositoryProvider`), so tests can override them.
- `presentation/`: screens plus an async notifier controller holding a Freezed UI model (e.g. `LoginController` → `AuthUiModel`).

**Networking.** Core owns one shared `Dio` and the error model (`packages/core/lib/src/network/`); Features call the backend through retrofit clients.
- `dioProvider` (keep-alive) is `createDio(config.apiBaseUrl, ...)` and is never changed after it is built: no base-URL, key or token setters. A client for another host builds its own Dio with `createDio(otherHost, reporter: ..., ...)`. Defaults: timeouts connect 10 s / send 30 s / receive 30 s (override per request through `Options`), `x-api-key` from `AppConfig.apiKey`, no global `Content-Type`.
- Interceptor order: app extras (`dioInterceptorsProvider`; its default is Core's auth interceptor alone, so an app that overrides it to add its own keeps `ref.watch(authInterceptorProvider)` in the list; extras run before retry) → breadcrumb (one per request: method, normalized path, status, duration) → retry (`dio_smart_retry`, 3 retries, only GET/HEAD/PUT/DELETE/OPTIONS, only on connection errors, connect timeouts, 408, 429 and 5xx) → logging (dev and staging only, `Logger('network')` at `FINE`, `Authorization` and `x-api-key` redacted). No cache and no connectivity check in Core; a Feature that needs caching adds it to its own Dio.
- A Feature's client is a `@RestApi()` class in its `data/` with the endpoint paths as annotations (e.g. `features/authentication/data/auth_api.dart`), built with `ref.watch(dioProvider)` and `errorLogger: apiParseErrorLogger` (so decode failures keep their request). An abstract repository sits above it, and its implementation wraps every call in Core's `ApiCall` from `apiCallProvider`: `apiCall(() => api.login(body))` for methods returning the model, `apiCall.unwrap(() => api.x())` for methods returning `BaseResponse<T>`. Rerun build_runner after changing a client.
- `BaseResponse<T>` (`base_response.dart`) is Core's default envelope; edit its fields and the unwrap rule next to them to fit your backend. 2xx with `success != true` throws `business` with `errorMessage ?? message`; a 4xx/5xx body's `errorMessage ?? message` is recovered too.
- Every failure becomes a sealed `ApiException`: `ApiConnectionException`, `ApiTimeoutException`, `ApiCancelledException`, `ApiUnauthorizedException` (401), `ApiForbiddenException` (403), `ApiNotFoundException` (404), `ApiServerException` (other 4xx/5xx), `ApiBusinessException`, `ApiDecodeException`, `ApiUnknownException`. Never check `statusCode` yourself; Dio throws on non-2xx.
- Reporting happens only in `ApiCall`: `server`, `notFound`, `decode` and `unknown` are reported once per launch per `<method> <normalized path> <status>` (numeric/UUID segments become `:id`; that string is the group key; tags `http.method` / `http.path` / `http.status`, extra `errorMessage` and the `requestIdHeaderProvider` header, default `X-Request-Id`); repeats and every other kind become breadcrumbs. Don't report an `ApiException` again.
- Showing errors: let the `ApiException` reach the UI as an `AsyncError` and call `ref.listenApiErrors(provider, context)` in `build` for a floating snackbar (skips `unauthorized`, which the auth Feature redirects, and `cancelled`). For a screen whose main data failed, use `ApiErrorView(error:, onRetry:)` in the `error` branch. Messages come from `ApiException.localizedMessage` / `apiErrorMessage` (the backend's message, else Core's default per kind). There is no global error observer.
- Tests: swap `dio.httpClientAdapter` for a fake adapter (see `packages/core/test/support/fake_http_adapter.dart`), pass `retryDelays: const <Duration>[]` to `createDio` to skip the waits, or override the repository provider.
- The auth interceptor adds `Authorization: Bearer <Session.accessToken>` to every request while signed in, reading the token per request (the Dio is never rebuilt). It never replaces an `Authorization` header the request already has. Requests that must go without a token (login, register, refresh) carry `@Extra(<String, Object>{skipAuthKey: true})` on the retrofit method.
- The default backend is reqres.in (test credentials in README); it doesn't wrap responses, so the demo auth client returns the models directly.

**Local storage.** Hive CE, in `<app support dir>/hive/` (`initHive` in `lib/hive/hive.dart`, which also registers the adapters and opens the unencrypted `prefs` box). Adapters are declared in `lib/hive/hive_adapters.dart` via `@GenerateAdapters([AdapterSpec<T>(), ...])`; add new persisted types there and rerun build_runner (`hive_registrar.g.dart` registers them).
- Anything secret goes in a box opened with Core's `openEncryptedBox<T>(name)`: AES-256 with one random key (`Hive.generateSecureKey`) created on first use and kept in `flutter_secure_storage` (`SecureHiveKeyStore`; tests pass an in-memory `HiveKeyStore`). A box that can't be opened, or was written with a lost key, comes back empty instead of failing. If the key store throws on read (Keychain locked before first unlock), the open fails and nothing is overwritten, so a later open finds the same key and data; only a missing or malformed key gets a new one. Open each box once through a keep-alive provider that tests override.
- Box owners: Core owns the `session` box (`sessionBoxProvider`), which also holds the last loaded `Permissions` (JSON under `permissionsKey`), so clearing it at logout deletes them; the auth Feature owns the `credentials` box and `LoginCredentials` (`features/authentication/data/credentials_store.dart`). No per-user boxes.
- Android backups exclude `files/hive/` and flutter_secure_storage's shared prefs (`android/app/src/main/res/xml/backup_rules.xml` and `data_extraction_rules.xml`; keep the two in sync); `allowBackup` stays on. macOS needs `keychain-access-groups` in both `macos/Runner/*.entitlements` for the key.

**Session.** Core's `sessionProvider` (keep-alive `AsyncNotifier<Session?>`) is loading at startup, then the saved `Session {accessToken, refreshToken?, userId?}` or `null` (signed out). The token is opaque: never decode it. The Session always survives a restart; nothing is checked over the network at startup.
- The auth Feature signs in with `ref.read(sessionProvider.notifier).signIn(Session(...))` after a successful login; pass `userId:` when the backend returns one (it only feeds `ErrorReporter.setUser`).
- Any screen logs out with `ref.read(sessionProvider.notifier).logout()`: it calls `SessionHooks.logout` (if the app overrides `sessionHooksProvider`) without waiting, clears the tokens whatever the hook does, and calls `setUser(null)`. The session is already being cleared when the hook runs, so the hook sends the token from the `Session` it receives itself.
- Every provider that holds user data does `ref.watch(sessionProvider)`, so it rebuilds on logout. A token refresh changes the Session too, so it also rebuilds then.
- Token refresh (only on a 401, never ahead of expiry): give `SessionHooks(refresh: (Session current) async => Session(...))` through `sessionHooksProvider`. The hook's retrofit method carries `skipAuthKey`; copy `refreshToken` / `userId` from `current` when the backend doesn't resend them. The auth interceptor runs one refresh at a time for all failing requests, saves the new tokens (`SessionNotifier.updateTokens`) and replays each request once; a request sent with an older token is replayed without a refresh. No hook or no refresh token, or the refresh rejected with 400/401 (`DioException`, `ApiUnauthorizedException` or `ApiServerException` 400): `SessionNotifier.expire()` signs out and sets `sessionExpiredProvider`, waiting requests fail as `unauthorized`, the router goes to `/login?from=<location>`, and the login screen shows `CoreLocalizations.authSessionExpired` until the next sign-in. Any other refresh failure (no network, 5xx) keeps the user signed in and fails the waiting requests with that error. A 401 on a replayed request is reported once (`UnauthorizedAfterRefreshException`, non-fatal), then signs out.
- Remember me only pre-fills the login form: the credentials are saved when it is ticked at login, deleted when it is unticked, and kept on logout. They never sign anyone in.

**Permissions.** Core's `Permissions {areas, components}` (`packages/core/lib/src/permissions/`): granted Permission areas plus Component rules (`ComponentState.hidden` / `readonly` / `disabled`); `can(area)` checks an area and `stateOf(componentKey)` returns a control's rule (`null` = none). The auth Feature supplies them through the optional `SessionHooks.loadPermissions` hook (`Future<Permissions> Function(Session)`), which fetches the backend's data, keeps this app's branch and flattens it; it gets the `Session` because it runs before the session is saved, so a real loader sends `Authorization` itself. No hook means `Permissions.unrestricted` (everything allowed). The template's hook is the demo `loadDemoPermissions` (`features/authentication/data/demo_permissions.dart`): profile, settings and orders (no screen), not reports, plus one Component rule per state. Area and component keys are typed constants in `lib/shared/permission_keys.dart`.
- `permissionsProvider` (`Permissions?`) watches `sessionProvider`: `Permissions.none` signed out, `null` while not known yet, else the list. `permissionsServiceProvider` (`PermissionsService`) loads and reloads.
- Login: the login controller calls `permissionsService.loadForSignIn(session)` before `sessionProvider.notifier.signIn(session)`, so login completes only once they have loaded and no screen sees them missing. If the load fails and nothing is saved, it rethrows and the login fails with the error's message (fail-closed); with a saved copy, that copy is used. Any other sign-in path must do the same.
- Reloads: once per launch (a cold start uses the saved list at once and reloads in the background; a cold start with nothing saved holds guarded routes on the splash until it lands), and at most once per launch after a 403 (`ApiCall` calls `reloadAfterForbidden` for each `ApiForbiddenException`; the user still sees the default message). One reload at a time; a failed reload keeps the current list (nothing known: `Permissions.none`). Never on app foreground.
- Controls: wrap one in `PermissionGate(componentKey: AppComponents.x, child: ...)`: hidden removes it, readonly shows it as it is but absorbs taps and focus, disabled also greys it out (`disabledColor` opacity). In code, `ref.watch(canProvider(area))` and `ref.watch(componentStateProvider(key))`. All three are fail-closed while the permissions are unknown (`false` / hidden). The demo controls are on the home screen (`features/home/presentation/widgets/component_rules_demo.dart`).
- Menu: Core's `PermissionMenu {routes, underConstructionPath}` maps area keys to routes; `filter(keys, can: (String area) => ref.watch(canProvider(area)))` keeps the granted keys in order, and a key without a route leads to `SGRoute.underConstruction` (Core's `UnderConstructionPage`). The app owns the key list (fixed here, or built from the backend's tree) and the look: `lib/router/app_menu.dart` and the home screen's end drawer (`AppMenuDrawer`).
- Key check: in debug builds `permissionKeyLogProvider` logs (`permissions` logger, once per key) every key checked through those providers or the gate that no loaded tree contained, since a component key the backend never sends always allows. Only areas and keys with a rule count as seen, and route areas checked by `permissionRedirect` are not noted.
- Tests override `sessionHooksProvider` with `SessionHooks(loadPermissions: ...)`; without it everything is allowed. `test/app/permissions_flow_test.dart` drives login, the launch reload, the guard, the demo gates and the menu.

**Routing.** `lib/router/app_router.dart`: `goRouterProvider` builds a `GoRouter`; routes are named by the `SGRoute` enum (`SGRoute.home.route` → `/home`). It starts on `/splash` (the splash passed to `bootstrap`) and uses Core's `sessionRedirect` with `refreshListenable: sessionListenableProvider`: splash while the session loads, then signed out → `/login` (add pages open to signed-out users to `publicPaths`), signed in → `/home` from login and splash (or back to `from` when an expired session sent the user to `/login?from=<location>`; pass `uri: state.uri` and `expired: ref.read(sessionExpiredProvider)`). Never navigate to home after login or to login after logout yourself: changing the session is enough, and the redirect replaces the stack so back can't undo it. The redirect is `sessionRedirect(...) ?? permissionRedirect(...)`: session first, then the permission guard, which sends a route whose area is missing to Core's `NoPermissionPage` at `SGRoute.noPermission` (links and direct `go()` included) and holds a guarded route on the splash while the permissions are unknown. A route opened before the session or the permissions are known waits on `/splash?from=<location>` and continues there once they are (same safe-location rules as the login `from`): pass `uri: state.uri` to both and `holdOnSplash: permissions.value == null` to `sessionRedirect`, which keeps the splash with a pending `from` instead of sending a signed-in user home. Each route declares its area on its `SGRoute` value (`reports(area: AppAreas.reports)`); a value without `area:` is open to any signed-in user (keep home open, the no-permission page leads there). The guard reads the matched route's name (`state.topRoute`), and `refreshListenable` merges `sessionListenableProvider` and `permissionsListenableProvider`. Every `GoRoute` must set `name:` (`SGRoute.<x>.name`): Core's `NavigationBreadcrumbObserver` (in the router's `observers`) records push/pop/replace breadcrumbs by route name only and skips unnamed routes (go_router names its own pages by path when a route has no `name`, so an unnamed route is either missing or recorded by its path). `test/router/app_router_test.dart` enforces it. Transitions come from the `.fade()` / `.slide()` extensions on `GoRoute` in Core (they keep the route `name`) (`FadeGoRouteExtension` / `SlideGoRouteExtension` in `packages/core/lib/src/router/`), both exported by `package:core/core.dart`.

**Theming / i18n.** FlexColorScheme light/dark in `lib/app/theme.dart`, passed to `bootstrap` and read by `MyApp` through `konteynerThemeProvider`. Core's `themeModeProvider` (system/light/dark) and `localeProvider` (`null` = follow the device) are saved in the unencrypted Hive `prefs` box (`prefsBoxName`, opened by `initHive`; tests override `prefsBoxProvider`); `MyApp` passes them to `MaterialApp`, and the home screen's theme and language tiles set them.

Strings use Flutter's gen-l10n, one translation set per package: the app's `lib/l10n/app_<locale>.arb` → `AppLocalizations` (all Features share it), Core's `packages/core/lib/l10n/core_<locale>.arb` → `CoreLocalizations` (error messages, session expired, Remember me, no-permission / under-construction pages, update dialog). Each package has `generate: true`, its own `l10n.yaml`, `flutter_localizations` and `intl: any`. Rules:
- ARB key order: `@@locale` first, then keys sorted by name, each `@key` metadata block right after its key. `test/l10n/arb_order_test.dart` checks every `*.arb` in the repo.
- Every app key starts with its Feature's name (`homeIntro`, `loginTitle`); `appTitle` is the app title (`MaterialApp.onGenerateTitle`). Add `@key` metadata only for placeholders or translator notes.
- English is the template and fallback. A new locale needs an ARB file in every package with strings (a missing key falls back to English, a missing file makes that package's delegate unsupported); `AppLocalizations.supportedLocales` is the only locale list, and iOS also lists locales in `CFBundleLocalizations` (`ios/Runner/Info.plist`).
- One delegate list, `appLocalizationsDelegates` in `lib/app/l10n.dart`, feeds `MaterialApp` and the tests: the app's delegates, `CoreLocalizations.delegate`, material_ui's `GlobalMaterialLocalizations.delegates`, plus one line per Module with strings.
- To change Core's wording, edit `packages/core/lib/l10n/*.arb` directly; there is no override mechanism. Code without a `BuildContext` uses `lookupCoreLocalizations(locale)`.
- On a merge conflict in generated l10n Dart, take either side and rerun `flutter pub get`.

**Design tokens and fonts.** `lib/app/tokens.dart` holds the hand-written raw values (scheme colors, status colors, spacing, radii, font family and type scale); only `lib/app/theme.dart` reads it. `buildAppTheme()` turns them into light and dark FlexColorScheme 9 `ThemeData` and fills Core's `KonteynerTokens` `ThemeExtension` (spacing, radii, `success` / `warning` / `info` and their on-colors) for both. Core reads it only via `KonteynerTokens.of(context)`, which falls back to `KonteynerTokens.fallbackLight` / `fallbackDark`; app-only extensions go next to it in `theme.dart`. Fonts load through google_fonts from the files bundled in `assets/fonts/` (named `<Family>-<Weight>.ttf`, e.g. `Roboto-Medium.ttf`); `buildAppTheme()` sets `GoogleFonts.config.allowRuntimeFetching = false` and registers `assets/fonts/OFL.txt` with `LicenseRegistry`. Changing the font or using a new weight means bundling its files (and license) there; `test/app/theme_test.dart` fails when a used file is missing.

## Testing pattern

Unit-test controllers with a `ProviderContainer` and `overrides` (fake repositories via `overrideWithValue` / `overrideWith(Fake.new)`), keeping autoDispose providers alive with `container.listen(...)`. See `test/features/login_controller_test.dart`. App tests get in-memory `prefs`, `session` and `credentials` boxes from `test/support/storage.dart` (`TestStorage.open()`, then `...storage.overrides`); `test/app/session_flow_test.dart` drives the real router through restart, redirect and logout.
